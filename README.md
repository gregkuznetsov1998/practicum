### 1. Описание функциональности монолитного приложения

Система позволяет работать с датчиками температуры. Другие типы не предусмотрены

1. Операции с датчиками:
	* Получение информации о текущей температуре с определенного датчика
	* Получение информации о текущей температуре со всех датчиков
	* Выключить или включить датчик
	* Добавить новый датчик или удалить существующий

### 2. Анализ архитектуры монолитного приложения

* Язык программирования: Go
* База данных: PostgreSQL
* Архитектура: Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.
* Взаимодействие: Синхронное, запросы обрабатываются последовательно.
* Масштабируемость: Ограничена, так как монолит сложно масштабировать по частям.
* Развертывание: Требует остановки всего приложения.

### 3. Определение доменов и границы контекстов

Список доменов:
1. Управление устройствами
2. Мониторинг устройств

Контекст здесь один и он распространяется на оба домена, так как у нас всего 1 сущность "Датчик" и определяется везде одинаково

### 4. Проблемы монолитного решения

Текущее монолитное решение не имеет критических проблем в рамках существующих условий эксплуатации.

В будущем будут проблемы с расширяемостью и отказоустойчивостью системы, так как есть синхронная зависимость от temperatureAPI.

# Задание 4. Создание и документирование API

### 1. Тип API

1. Характер операций
	Синхронные запросы-ответы: Большинство операций в системе требуют немедленного ответа:

	Пользователь ожидает актуальные данные сенсоров при запросе

	CRUD операции с устройствами должны подтверждаться сразу

	Обновление значений сенсоров требует синхронного подтверждения

	Низкая латентность: HTTP обеспечивает минимальную задержку для операций в реальном времени

2. Простота системы
	Минимальная сложность: Для текущего масштаба системы (3 основных микросервиса) HTTP-коммуникация проще в реализации и поддержке

	Отсутствие промежуточных компонентов: Не требуется развертывание и поддержка брокеров сообщений (RabbitMQ, Kafka)

	Прямая связь: Позволяет сохранить простую архитектуру "запрос-ответ"

3. Типы данных
	Небольшие объемы: Передаются небольшие JSON-объекты (метаданные сенсоров, значения показаний)

	Низкая частота обновлений: Нет потоковой передачи данных с высокой частотой

	Отсутствие событийного потока: Нет требований к обработке потоков событий

4. Требования к согласованности
	Strong Consistency: Для операций с устройствами критична немедленная согласованность данных

	Прямая валидация: Возможность сразу вернуть ошибку при невалидных данных

	Простая отладка: Синхронные вызовы легче отслеживать и дебажить

5. Интеграционные паттерны
	API Gateway: Естественно работает с HTTP-бэкендами

	Сервис-ориентированная архитектура: Прямые вызовы между сервисами соответствуют SOA-принципам

	RESTful интерфейсы: Стандартный подход для ресурсо-ориентированных систем
